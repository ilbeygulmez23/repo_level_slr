- Draft: "≥10 stars, updated within the last three years, all tests passing"; table row 104; provenance row "H (reverse-eng.) | Up | pytest | recency filter"
- Verdict: MISLEADING (only the contamination-defence cell; the rest is VERIFIED)
- Evidence: "We require each repository to have at least 10 GitHub stars" ; "Only repositories that have been created or updated within the past three years are considered, allowing NL2Repo-Bench to reflect contemporary coding practices and avoid outdated dependency ecosystems." ; "its official version must successfully pass all of them" (§3.1.1). The paper does not offer it as a contamination defence and names no contamination defence at all. Change the defence cell to "none stated". ### C12 — RepoModBench2026 [A12]
- Draft: 21 repos; spec = source repo; tests "Up (interface-filtered)"; oracle CLI/REST; defence "hidden tests"
- Verdict: VERIFIED (the defence cell needs framing)

- Draft 1: "Almost every benchmark mines public GitHub or PyPI repositories filtered by popularity (stars), activity, and presence of a passing test suite."

### C17 — DeNovoSWE2026 (arxiv:2606.10728) [B3]
- Draft: spec by "a GPT-5.x draft--critic--repair loop"; "builds 4,818 instances this way"; tests "Up", oracle "pytest"; defence "sandbox, no net".
- Verdict: VERIFIED for spec and count. CORRECTED for "no net" and "pytest".
- Evidence:
  - "an iterative multi-agent pipeline (Draft-Critic-Repair)" ... "all agent modules and LLM-as-judge components are implemented with GPT-5.4 and GPT-5.5." (Sec. 3)

## Cross-study claims

### X1 — "Almost every benchmark mines public GitHub or PyPI repositories filtered by popularity (stars), activity, and the presence of a passing test suite."
- Support: partial. Star filters appear in 7 of the 13 benchmarks checked (C14). A passing-test filter is explicit in only 4 (NL2Repo, RAL-Bench, RepoMod, REPOCOD). The counter-examples (RepoGenesis, JavaBench, the forward-spec benchmarks) are in the same section.
- Rewording: "Most benchmarks we checked mine public GitHub repositories filtered by stars (7 of 13); several also require the upstream tests to pass [NL2Repo, RAL-Bench, REPOCOD, RepoMod]."

### X2 — "Popularity filters ... select exactly the repositories most likely to appear in pretraining data"
- Support: this is the authors' inference with no citation. RAL-Bench itself concedes "we do not claim that pretraining exposure can be fully ruled out" (C2).
- Rewording: cite RAL-Bench's concession, and state it as a plausible tension rather than a fact.

### X3 — "The number of independent repositories is small ... scale of other core benchmarks is similar"
- Support: yes, by the table counts (C8-C13). But DeNovoSWE (4,818) is a training set, and REPOCOD has 11 repos and DevEval 117. "Similar" is loose: the counts range from 6 to 104.
- Rewording: "Evaluation benchmarks contain 6-104 repositories (Table)."

### X4 — "Few studies report variance: many core evaluations are single runs, for cost reasons."
- Support: the single-run part holds. The cost reason does not: only JavaBench cites cost, and that is for its n=5 sampling (C14). Exceptions with repeated runs: RAL-Bench (3 runs plus a 5-rerun Std/CV table), RepoGenesis (5 runs), E2EDev (3 runs, SD), RepoClassBench (6 runs, SD), PaperBench (3 runs, SEM), DeNovoSWE (3 trials, means), HumanEvo (3 runs). CLI-Tool-Bench and RepoZero give bootstrap CIs over tasks.
- Rewording: "Most evaluations are single runs, often greedy, and give no reason; repeated runs appear in RAL-Bench, RepoGenesis, E2EDev and PaperBench."

### X5 — "the model family that writes the specification is often also among the models evaluated, and specification quality is rarely validated independently"
- Support: yes, with qualification (C21). The overlap holds in BeyondSWE (Gemini 3 Pro), RoleBased (GPT-5), VibeCodeBench (GPT-5.x), RepoClassBench (GPT-4), E2EDevBench (Gemini-2.5-Pro, which is also test migrator and judge), WebGen-Bench (GPT-4o) and RealDevWorld (Claude-3.5-Sonnet). All are preprints except RoleBased (IEEE Software). Validation runs from none (RepoClassBench, DeNovoSWE) to a PM review (VibeCodeBench). No study measures self-preference.
- Rewording: "In at least seven benchmarks, 2024-26 preprints for the most part, the spec-writing model also appears among the evaluated models; none measures whether this favours that model."

### X6 — "Execution against the reference guarantees that each test is consistent with the reference, but not that the tests cover the specification."
- Support: this is a logical inference, and ProgramBench states it ("a finite test suite necessarily under-approximates"). ProgramBench is the one exception that measures line coverage (79.7%) (C39).
- Rewording: keep, and add the ProgramBench coverage figure.

### X7 — "Test adequacy is rarely measured."
- Support: the draft's exception list is incomplete and contains an error (YABLoCo). Adequacy is measured by ProgramBench, MRG-Bench, YABLoCo, Oxidizer, TRAM and RepoMasterEval (C40).
- Rewording: "Few benchmarks report test adequacy: ProgramBench (line coverage), MRG-Bench and YABLoCo (coverage-filtered targets), and RepoMasterEval (mutation score)."

### X8 — "Contamination is a first-order threat"
- Support: mixed. Measured leakage is small (EvoCodeBench CDD 0.7-2.2%; MRG-Bench 4.9-7.8%). Commit0 concludes that memorisation "is not a major factor". The large effects come from ObfusEval (relative drops of 15-62%, GPT-4-era, preprint) and the EvoCodeBench-DevEval gap, which the authors partly attribute to difficulty. The evidence is mostly from 2023-24 models.
- Rewording: "Studies that measure contamination directly, all with 2023-24 models, find low n-gram or CDD leakage but large drops under obfuscation."

### X9 — "No defence is complete. Recency filters limit ..., obfuscation changes the task distribution, and transformation changes the task itself."
- Support: this is the authors' reasoning, uncited. RealBench's own model release dates postdate its cutoff (C10), which supports "recency filters age".
- Rewording: keep it as an inference, and cite the RealBench/MRG-Bench examples of cutoffs that predate the models.

### X10 — "Three further forms of leakage are documented. They are easier to fix than contamination and are often overlooked."
- Support: "easier to fix" and "often overlooked" are uncited. They are plausible for tests and network but not demonstrated.
- Rewording: drop the evaluative clause, or say "each has a direct fix (masking, no network, disjoint test sets)".

### X11 — "Agents with network access find the original code"
- Support: only ProgramBench measures this (20-36% flagged, from LM-judge majority with low agreement, kappa 0.16-0.60; preprint; 2025-26 models). CodeAgent gives no evidence (C49). The chess example is a local library import, not network lookup (C50).
- Rewording: "In ProgramBench, LM judges flag 20-36% of runs by three 2025-26 models as cheating when internet is enabled, mostly source lookup."

### X12 — "When generation can see the oracle, a pass rate measures how well the system optimises against that oracle, not how correct its code is."
- Support: this is an inference with no measurement. No study quantifies the effect of disjoint vs shared tests. SpecAgent (Pass@1 20.20 vs 24.08) and DyRetriever measure context leakage, not test feedback.
- Rewording: "... the pass rate also rewards optimisation against that oracle", together with the recommendation.
