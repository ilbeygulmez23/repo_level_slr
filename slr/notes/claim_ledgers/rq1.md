## Cross-study claims

### X1: "Across all types, the size of the target is the strongest single predictor of difficulty" (l.120)
- Support: No. No cited study compares size against other predictors such as specification length or domain, and there is no evidence for paper-to-repo, app or reconstruction types. Each evidence point is a within-benchmark correlation in which size is confounded with project identity (RepoMod has 3 small projects). JavaBench says nothing about size. The studies also use different model generations: RealBench with GPT-4o/Sonnet 4, NL2Repo with Sonnet 4.5/GPT-5, RepoMod with Opus 4.5/GPT-5.2. All except RealBench are preprints.
- Rewording: "Within each benchmark that reports it, pass rates fall sharply with target size. This holds for RealBench (FSE'26, GPT-4o/Claude Sonnet 4 era), NL2Repo-Bench and RepoMod-Bench (preprints, 2025–26 models, the latter with only three projects under 10k LOC), and JamBench (80.4% to 5.7% runtime pass, preprint). No study isolates size from other factors."

### X2: "specificity and oracle coupling tend to rise together, because a specification must fix whatever the oracle will test" (l.114)
- Support: Partial. NL2Repo states explicitly that the spec must cover every API the tests exercise, DeNovoSWE generates test-aligned docs, and RAL-Bench supplies the module surface to avoid "evaluation artifacts". The counter-examples CLI-Tool-Bench and RepoMod pair low internal specificity with black-box oracles, which is consistent with the claim. Evidence is all from preprints.
- Rewording: "In the benchmarks that discuss it (NL2Repo-Bench, DeNovoSWE, RAL-Bench; all preprints), specification detail is driven by what the reuse-based test oracle requires. Benchmarks with interface-level oracles (CLI-Tool-Bench, RepoMod-Bench) can leave internals unspecified."

### X3: "Several studies recognise the tension explicitly" (l.107)
- Support: Overstated. RAL-Bench and CLI-Tool-Bench discuss it. NL2Repo does not frame it as a tension (C37). BeyondSWE gives no rationale (C38). The RepoMod characterisation is wrong (C40).
- Rewording: "Some benchmark designs respond to this tension: ..." Then correct the bullets per C37, C38 and C40.

### X4: "Without it, pass rates cannot be compared across benchmarks" (l.114)
- Support: This is an argument, not an empirical finding; no study attempts a cross-benchmark comparison. It is acceptable if phrased as a position: "We argue that without it, pass rates are not comparable ..."

### X5: "Most core studies run autonomous agents with generous budgets" (l.117)
- Support: Only two examples are given (NL2Repo, ProjDevBench). There is no corpus count, and "generous" is undefined.
- Rewording: give a count from the corpus coding (e.g. "N of M core studies evaluate autonomous agents") or say "Many recent (2025–26) benchmarks run autonomous agents over long horizons, e.g. ...". Also fix the 180-turn figure (C41).

### X6: Human-steered studies "supply evidence on quality dimensions that benchmarks miss" (l.119)
- Support: Plausible for CursorDesignIssues (design smells via SonarQube/CodeScene) and Prompt-to-Product (perceived usability). The CBA study is about prompting behaviour, not output quality. All are preprints or a workshop paper.
- Rewording: "... supply evidence on design quality [Cursor] and perceived usability [Prompt-to-Product] that pass-rate benchmarks do not measure."
